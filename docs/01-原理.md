# 原理：为什么智能体要长这样

> 这一篇不写代码，只回答一个问题：把"大模型"变成"智能体"，中间补了什么？

---

## 一、大模型本身缺什么

一个大模型，本质上是一个函数：

```
回答 = 模型(提示)
```

它能理解、能生成，但有三个先天限制：

| 限制 | 后果 | 补什么 |
|---|---|---|
| 不知道你的实际情况 | 它不知道今天的天气、你的库存、你的文件 | **工具** |
| 不会自己动手 | 它只能"说"，不能"做" | **工具** |
| 只看得到这一次输入 | 它不记得上一轮聊了什么 | **记忆** |

所以，智能体不是"更聪明的大模型"，而是**给大模型补上手脚和记忆的一套工程结构**。

```
智能体 = 大模型 + 工具 + 记忆 + 循环控制
```

---

## 二、工具：给模型一双手

工具的本质是一次**函数调用**，但它有个关键设计：

> 模型不能执行代码，它只能"说"出想调用什么。

于是流程变成：

```
模型输出：{"tool": "calculator", "input": {"expression": "24*7"}}
    ↓  （程序解析）
程序调用：calculator("24*7")
    ↓
程序把结果："168" 作为 Observation 塞回提示
    ↓
模型看到结果，给出最终回答
```

这里有两个容易忽略的点：

1. **工具描述是提示词的一部分。** 模型只能看到工具的 `name`、`description`、`parameters`。描述写得含糊，它就会在错误的时候调用、或者不去调用。
2. **工具出错不能炸掉整个流程。** 一个成熟的工具层会把所有异常收敛成"结果对象"（本仓库的 `ToolResult`），让 Agent 有机会重试、换工具，或如实告诉用户失败。

---

## 三、循环：ReAct 在做的事

只调一次工具，能解决的问题很有限。真正有用的是"调一次 → 看结果 → 根据结果决定下一步"。

ReAct（Reasoning + Acting）就是这个循环：

```
Thought   → 我要干什么
Action    → 调哪个工具
Action Input → 参数是什么
Observation  → 工具返回了什么（由程序填）
...重复...
Final Answer → 结论
```

关键在于：**Observation 不是模型编的，是程序填的。**

这也是为什么 ReAct 的轨迹（trace）特别有价值——它是可审计的。出问题时，你能精确指出是哪一步、哪个工具、什么参数导致的。

但循环必须有两个刹车：

- **步数上限**（`max_steps`）：防止无限转圈；
- **明确失败**：步数用完还没答案，就报告"没得出答案"，而不是编一个。

---

## 四、记忆：不是越多越好

对话历史会进入每一次请求，所以它是**有成本的**：

- 成本：token 越多越贵、越慢；
- 质量：无关的历史会干扰判断（上下文噪声）。

三种常见策略：

| 策略 | 做法 | 适合 |
|---|---|---|
| 无记忆 | 每次只发当前一轮 | 独立问答、翻译 |
| 窗口记忆 | 只保留最近 N 轮 | 大多数对话产品 |
| 摘要记忆 | 超长时把旧内容压成一段摘要 | 长会话、任务型助手 |

真实产品通常是**三件套**：最近 N 轮（保精度）+ 长期摘要（保脉络）+ 向量检索（保事实）。本仓库实现了前两件，第三件留给你练手。

---

## 五、多智能体：为什么要拆

一个 Agent 同时负责"想"和"做"，提示词会变得又长又杂，模型容易顾此失彼。

拆成三个角色：

```
Planner   把目标拆成子任务
Executor  逐条执行（可调工具）
Reviewer  组装、检查、如实报告
```

好处不是"更智能"，而是：

- 每个角色的提示更聚焦，输出更稳定；
- 失败时能定位到具体角色；
- 子任务可以并行（本仓库为了简单是串行）。

坏处也很实在：**角色越多，调用次数、延迟和成本越高**。三个角色是常见的最优区间，别轻易堆到十个。
